NIGHT SIGNAL 運用方針

このページは、毎晩のブリーフを作るための最新版ルールです。過去の指摘をそのまま積み上げるのではなく、現在有効な考え方だけに整理します。

目的

NIGHT SIGNALの目的は、ユーザーが毎日大量のWeb、公式発表、ニュース、SNS/X、YouTube、専門メディア、現地媒体を巡回しなくてもよいように、重要情報を漏れにくく集め、短時間で読める形に整理することです。

最優先は情報の抜け漏れを減らすことです。見た目、短さ、件数の少なさより、必要な情報が不足していないことを優先します。

方針文だけでは再発防止にならない。公開前に機械的な品質ゲートを通し、当日版がない、古いカードが残る、当日/前日カードが少なすぎる、抽出ログがない、日付が合わない場合は公開処理を失敗させる。

更新時間

  • 毎日16:00 JSTに調査を開始する。
  • 日本企業の決算、適時開示、ニュースが出やすい16時台以降の情報を必ず含める。
  • 21:50頃までに公開処理を行い、遅くても22:00 JSTには固定URLで最新版を読める状態にする。
  • 23時間固定ではなく、必要十分な調査時間を確保する。情報量が多い日、決算日、レース週、打ち上げ前後などは探索軸を増やす。

調査順序

最初にカテゴリ別カードを作らない。まず直近24〜72時間の変化点を横断的に集める「変化点インボックス」を作り、その後で各カテゴリへ分類する。

  • 公式発表、IR、リリースノート、Status、規制当局、統計機関を確認する。
  • Reuters、Bloomberg、日経、WSJ、FT、主要現地紙、専門媒体を確認する。
  • SNS/X、YouTube、Hacker News、専門掲示板、現地観測者、中心人物・関係者の発信を確認する。
  • 株価、ETF資金フロー、為替、金利、PMI、FDI、外貨準備、販売台数、決算、ガイダンス、イベント予定を確認する。
  • 集めた候補を、鮮度、重要度、一次情報への近さ、ユーザー関心との接続で採用・保留・除外に分ける。

調査したつもりで終わらせないため、抽出ログには各カテゴリごとに「実際に確認した検索軸・媒体・一次情報・主要報道・SNS/X/YouTube確認状況」を残す。証跡がないカテゴリは調査完了扱いにしない。

カード削除後の再探索を必須にする。鮮度チェックで古いカードを削除した結果、カテゴリが0件または基準未満になった場合は、そのカテゴリを空欄で公開せず、カテゴリ別ウォッチリストを直接巡回し直す。削除は完了ではなく、再発見ゲートの開始点として扱う。

予定情報は、イベント日を過ぎた瞬間に結果情報へ上書き確認する。試合、レース、打ち上げ、決算、統計発表、製品発表は、予定表だけでは採用しない。公式結果、試合詳細、発表資料、主要報道、関係者コメントの順に確認し、予定のまま残っていたら公開前失敗とする。

情報源カバレッジ

根本対策は、掲載件数や当日追加数を見ることではなく、重要情報が発生し得る場所を実際に確認したかを検査することです。各カテゴリは、以下の情報源クラスを確認し、確認できなかったクラスは未確認としてログに残してから採用判断に進みます。

  • 発生源: 公式サイト、IR、適時開示、リリースノート、Status、規制当局、統計機関、特許・認可・入札、企業公式SNS。ニュースになる前の一次発生点を確認する。
  • 速報・主要報道: Reuters、Bloomberg、日経、WSJ、FT、AP、主要現地紙、日本語主要メディア。英語・日本語・現地語の見出し差を確認する。
  • 専門媒体: AI、半導体、自動車、F1、宇宙、アジア経済、投資、Bリーグ/バスケットボール、地域スポーツビジネスの専門メディア。一般紙では拾いにくい技術・業界文脈を確認する。
  • SNS/X: 公式アカウント、中心人物、専門記者、現地観測者、開発者、投資家、規制・業界関係者、コミュニティで話題化した投稿。投稿単体では採用せず、一次情報・複数投稿・専門媒体で裏取りする。
  • YouTube/動画: 公式チャンネル、決算説明、レース/宇宙の専門解説、現地観測、技術解説、イベント配信。見出しだけでなく投稿日、概要、映像内の主要論点、コメント欄で指摘されている論点を確認する。
  • データ・数値: 株価、出来高、ETF資金フロー、為替、金利、PMI、FDI、外貨準備、販売台数、生産台数、輸出入、決算予定、イベントカレンダー。ニュースがなくても異常値があれば候補化する。
  • 予定・カレンダー: 決算、製品発表、API更新、F1グランプリ、テスト、打ち上げ、規制判断、統計発表、中央銀行イベントを確認し、イベント前後の新情報を重点探索する。
  • 反証・漏れ確認: 「会社名 + today/news/update/problem/delay/launch/earnings」、日本語、英語、現地語、略称、子会社名、人物名、製品名で検索し、採用候補が本当に最新の主要論点を代表しているか確認する。

「カバレッジ済み」と言える条件は、少なくとも発生源、主要報道、専門媒体、SNS/X、YouTube/動画、データ、予定・カレンダー、反証検索の確認結果がカテゴリごとに残っていることです。全カテゴリで全情報源を同じ深さにできない場合でも、未確認の情報源クラスを抽出ログに明記します。未確認があるのに「網羅的に調査済み」と表現してはいけません。

完了判定は「カードが何件あるか」ではなく「どの情報源クラスを見て、何を採用・保留・除外し、何が未確認か」です。1件だけのカテゴリでも、各クラスを確認した結果なら許容します。逆に5件あっても、SNS/X、YouTube、データ、予定表、反証検索の証跡がなければ未完了です。

抽出ログのセルフチェック

抽出ログは作業メモではなく、抜け漏れを防ぐための検査表として扱います。ログの項目自体が不十分なら、情報収集を完了扱いにしてはいけません。

  • 各カテゴリで、確認した検索語、媒体、発生源、主要報道、専門媒体、SNS/X、YouTube/動画、データ、予定表、反証検索を明記する。
  • 採用した情報だけでなく、保留候補、除外候補、除外理由、未確認クラスを残す。後から「なぜ載せなかったか」を説明できない場合はログ不足とみなす。
  • カテゴリ固有の重要軸が入っているかを確認する。例: アジア経済なら統計・企業投資・工場建設・日系企業・為替・物流、宇都宮ブレックスなら試合結果・選手コメント・監督発言・怪我・契約・アリーナ/地域行政を必須軸にする。
  • 当日大きなニュースがないカテゴリでも、公式、主要報道、SNS/X、YouTube、データ、予定表を確認した結果なのかをログに残す。空欄や「特になし」だけでは不足。
  • 未確認クラスが残っている場合は、未確認のまま公開できる軽微リスクか、公開前に必ず潰す重大リスクかを分ける。重大リスク（決算本文、イベント結果、公式発表、固有名詞ニュース、SNSで大きく話題化した件）は未確認のまま完成扱いにしない。
  • 前回版と比べて当日追加が少ない場合、件数だけでなく「新規発生源・予定結果・SNS/X・YouTube・専門媒体・反証検索」を再走査する。単に“今日は少ない”と判断しない。
  • 公開前にログを読み返し、この項目でユーザーが後から「どこまで調べたか」「何が未確認か」「なぜこのカードが採用されたか」を確認できるかセルフチェックする。不十分ならログ項目を増やしてから公開する。

採用基準

  • 直近2〜3日以内の新情報、または直近イベントに直接つながる情報を優先する。3日を超える情報は原則として最新カードにしない。
  • 古い情報は、最新ニュースを理解する背景として必要な場合だけ採用し、「背景資料」と明記する。
  • 採用に迷う重要候補は、原則として掲載候補または抽出ログの保留に残す。不足より過剰を許容する。
  • 煽り、根拠不明の予想、一次情報へ戻れない投稿、関連が薄い穴埋め記事は採用しない。
  • 掲載件数は結果であり、根本チェックではない。1件しかないカテゴリや当日追加が少ない場合は、情報源カバレッジを満たした結果なのか、未確認が残った結果なのかを抽出ログで分かるようにする。

漏れ防止

企業名だけで検索しない。地域、子会社、製品ライン、サプライチェーン、人物、規制、指標、予定変更を分けて確認する。

  • 異常値を必ず探す。販売、生産、利益、受注、輸出入、PMI、為替、株価、ETF資金流入、打ち上げ予定、レース投入計画の急変は優先候補にする。
  • Honda中国販売急減、Toyotaインド新工場、F1次戦アップデート、Starship静的燃焼、OpenAI API更新、OpenAI Deployment Company設立のように、カテゴリをまたぐ材料を落とさない。
  • OpenAIだけ厚い、他カテゴリが薄いなどの偏りが出た場合は、実際の情報量による偏りか、作業上の偏りかを確認する。
  • 公開前に、発生源、主要報道、専門媒体、SNS/X、YouTube、人物発信、市場・指標、予定表、反証検索、除外記録の確認が済んでいるか点検する。
  • カテゴリ欄が0件になった場合、または前回より大きく減った場合は、情報が本当に少ないのか、削除後の再探索が漏れたのかを検証する。カテゴリ別ウォッチリストで新規・変更点を再確認するまで公開しない。

公開前の失敗判定

以下のどれかに当てはまる場合は、ページを完成扱いにしない。修正してから公開するか、抽出ログに未完成理由を明記する。

  • 当日版の night-brief-web-sample-YYYY-MM-DD.html、site/YYYY-MM-DD/index.html、site/index.html のいずれかが存在しない、または日付が当日でない。
  • GitHub Pagesの公開ワークフローだけが成功し、日次リサーチ生成・抽出ログ・当日詳細ページの作成記録がない。公開処理とリサーチ生成を混同してはいけない。
  • 各カテゴリで情報源カバレッジの証跡がない。
  • Web/公式/主要報道だけで終わり、SNS/X、YouTube/動画、データ、予定表、反証検索の確認有無が記録されていない。
  • OpenAI公式、主要日本語IT媒体、主要海外媒体のいずれにも大型ニュースがあるのに採用または保留に入っていない。
  • OpenAI、Honda、F1、SpaceX、SoftBank、ブレックスなどで、ユーザーの関心語に近い新固有名詞（例: Daybreak、Codex Security、Honda PU、Aston Martin、名古屋D、OpenAI評価益）が話題化しているのに、その語で直接検索した証跡がない。
  • 決算・IRが出ているのに、主要数字、セグメント別の読み方、投資/負債/NAV/ガイダンス、説明会資料の確認が本文へ反映されていない。
  • イベント日を過ぎた予定カードが、結果ページや主要報道で上書きされずに残っている。
  • 当日版成果物（固定URL、日付別URL、抽出ログ、詳細ページ）がないのに、前日版を再公開して更新完了にしている。
  • python3 scripts/quality_gate.py YYYY-MM-DD が失敗した。品質ゲートを通らない場合、GitHub Pagesへ公開してはいけない。
  • GitHub Actionsの公開処理で当日ファイルが存在しないのに、最新既存サンプルへフォールバックしている。これは禁止。必ずJST当日の日付を明示して同期し、当日ファイルがなければ失敗させる。
  • トップまたはカテゴリ欄に3日超の情報が多数残り、背景資料の明記もなく新規情報より目立っている。
  • トップの主要カードに、当日または前日の情報が十分にない。古い情報を残して件数を埋めるのではなく、再探索するか、未完成として止める。
  • 古いカードを削除した結果、カテゴリが空欄または極端に薄くなったのに、カテゴリ別ウォッチリストの再巡回証跡がない。
  • 同じ前日版のカードを並べ替えただけで、16:00以降の調査結果や未確認リスクが反映されていない。
  • 公開後に重要漏れが見つかった場合、ポリシーを書き足すだけでなく、実行プロンプト、抽出ログ形式、公開前ゲート、情報源カバレッジのどこが効かなかったかを検証する。

ページ構成

  • トップページには運用指示を書かない。毎晩読みたくなる編集コンセプト、今日の空気感、重要テーマの見取り図だけを出す。
  • トップのカードは、概要を読んで詳細を見るか判断できる短い要約にする。
  • 詳細ページは日本語で読める要約を置く。英語原文へ直接飛ばさず、まず日本語詳細ページへ誘導する。
  • 本文要約は短さより情報不足回避を優先する。重要な数字、日時、関係者、背景、前回からの変化、今後の日程は省略しない。
  • 参照先記事にグラフや表がある場合は、その内容を日本語で説明する。依頼がない限り自作図解は作らない。
  • 依頼がない限り、影響度、未確定点、次に見るサインなどの項目を増やさない。

公開と履歴

  • 固定URLは常に最新号を表示する。
  • 日付別ページは直近7日分だけ履歴として残す。
  • 抽出ログには、採用、保留、除外、未確認リスクを残す。
  • 22:00 JSTまでに当日版が固定URLへ反映されない場合は公開失敗として扱い、翌日を待たずに復旧版を作成する。
  • ユーザーから不要・不足の指摘があった場合は、個別対応だけで終わらせず、この方針へ反映できるか確認する。

今後の更新方法

新しい再発防止を追加する時は、末尾に追記し続けない。既存の該当セクションを書き換え、現在有効なルールとして読める状態を保つ。
